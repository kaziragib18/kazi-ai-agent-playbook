Why it exists

The problems it removes

AI agents are fast but undisciplined by default: they start coding before the problem is clear, re-explore the repo every session, skip checks, claim success without proof and grow long, expensive conversations. The playbook turns those habits into explicit rules.

AreaWithout the guideWith the guide
Starting workAgent writes code from a one-line prompt and guesses the rest.A "how we'll know it's done" check for every task; an approved brief before a new product and an approved plan before anything users will notice.
Understanding the repoRe-reads folders and files every session (10-20 exploratory calls).A 2-second recon script plus a saved project profile. Re-run only when dependencies or config change.
Joining a project mid-wayAgent either treats it like a new product or silently guesses the architecture.Missing product and architecture docs are drafted from the code, marked for you to correct, and kept current with every change.
QualitySecurity, legal, accessibility and ops get remembered only when someone asks.162 requirements filtered by level and project type; each has a command that proves it.
Honesty of results"Done" and "looks good" without evidence."Fine" needs file:line evidence or command output. Anything not checked is reported as "couldn't check".
Token costHuge instructions loaded every time; sessions grow until they drift.~2.9k-token core; playbooks and modules load only when needed; one task per fresh session with a file handoff.
Skills and toolsAgent uses whatever is installed, or nothing; duplicates pile up.Proposes a skill set for the product type, falls back when one is missing, and asks once before anything is installed.
Your controlAgent may push, deploy, add dependencies or install tools on its own.Installs, deploys, pushes, spending, deleting data, production actions and live legal text always need your approval.

StepWhat the agent doesWhat you see
PreflightReads the saved profile; re-runs recon only if manifests, lockfiles, config or CI changed. Configuration

The two dials: level and flags

Two settings decide which of the 162 items apply. You set the level; the agent proposes the flags from recon and you confirm them. In chat the agent describes the level in words ("a free beta with real users"), not as L1-L4.

Level: how much is at stake

LevelMeaningItems starting hereTotal in force
L1Prototype or demo, no real user data1111
L2MVP or beta: real users, free5869
L3Public launch or paid product77146
L4Scale or regulated: money at volume, health, minors, enterprise16162

"Total in force" is the ceiling; flags remove most of them for any given project.

Flags: what the project contains

FlagMeansDetected by recon?
auth db apiSign-in, a database, server routesyes
ai pay emailLLM calls, payments, sending emailyes
upload renderFile uploads, headless browser / PDF renderingyes
ui publicA user interface, publicly indexed pagesyes
adminAdmin routes or roleshint
minors libChildren may sign up; the project is a packageask you
Example: a free MVP with sign-in and a database (free beta; ui auth db api) never sees payment, email, minors or launch-and-above items. A static landing page (ui public) never sees database or auth items. If the brief and the profile disagree, the profile wins for level and decisions, the brief for product scope.

Mid-project

Joining an existing project

Most work happens in repos that already exist. Phase 0 doesn't fit (the product is already running), and guessing the architecture is how agents break things. So on the first session in a repo with no profile or missing docs, the agent builds the same shared picture Phase 0 would, but from the code instead of an interview. It runs quietly inside the preflight, not as a separate ceremony.

1 · DetectRecon, then check the five docs: profile, brief, architecture, essentials, CLAUDE/AGENTS
→
2 · Say what's missingOne line: "No brief or architecture summary yet; I'll draft both from the code"
→
3 · Draft from codeRoutes, data model, manifest, entry points; unknowns marked "dev to fill"
→
4 · You correctAt a natural pause, batched with other questions; not a blocking gate
→
5 · Do the taskThe session continues with what you actually asked for
DocumentHow it is draftedRule
docs/agent-profile.mdFrom recon: stack, flags, source dirs, routing; level asked onceSame as any first session
docs/PRODUCT-BRIEF.mdPersona, problem and value loop inferred from UI copy, routes and data model. Success metric, monetization and constraints are marked "unknown, dev to fill", never guessedEvidence, not invention
docs/ARCHITECTURE.md and ARCHITECTURE-ESSENTIALS.mdFrom the actual source tree: entry points, data layer, the boundaries that exist today, integrations from the manifest and env. Shared understanding

Architecture docs that stay current

Two files with two audiences. A fresh session, human or agent, reads the short one first; the long one is the reference. A stale architecture doc is worse than none, because it misleads the next session, so keeping them current is part of "done".

FileForSizeChanges when
docs/ARCHITECTURE.mdDeep reference: system overview, components, the main data flows, storage, integrations and their failure modes, non-obvious decisions (linking the decision records), known limitsAs long as neededAn architectural decision changes: a new subsystem, a storage change, a new auth model. Not every commit
docs/ARCHITECTURE-ESSENTIALS.mdWhat anyone must know before touching code: the invariants that are easy to break and expensive to unwind, commands (or a pointer to CLAUDE.md), gotchas already hit once, pointers for moreUnder ~200 linesEvery task that touches architecture, in the same commit as the change

The drift rule

MomentWhat the agent does
A task changed architectureUpdates ARCHITECTURE-ESSENTIALS.md in the same commit. An architecture change without the doc update is not done.
Drift noticedThe doc says X, the code does Y: fix the doc now, or tell you. Never leave it for later; a later session can't know the doc was already known to be wrong.
End of a long sessionThe handoff note says whether the essentials doc still matches what was built; if not, fixing it is the first line of the next task.
Your project has its own conventionYour names, format and rules win (for example a CLAUDE.md that says which docs to keep current). The playbook only sets the floor for projects that have none.

Skills and tools

Why this way of choosing skills is better

Without rules, an agent uses whatever skill it notices first, several at once, or none. The guide makes the choice predictable, cheap and always under your control.

Rule in the guideWhat usually happens without itWhy the guide's way is better
Pick from the task, not from habitThe agent reaches for a familiar skill even when the task needs a different one.The router and the table on page 16 give the same answer every time, across sessions and teammates.
Only skills actually installedThe agent "calls" a skill that does not exist in this setup, or describes one from memory.No invented skills; the session's own list is the only source of truth.
One skill per capabilityTwo overlapping skills give conflicting advice (two style presets, two workflow packs).One clear direction; no muddled design or duplicated steps.
Capabilities, not brand namesA gap stays open because the one named tool isn't installed.Any installed tool with the capability counts, so new tools slot in without changing the playbook.
Built-in fallback for every rowWork stops, or quality drops, when a skill is missing.Work never blocks; the fallback applies the same rules by hand.
Ask once, batchedThe agent interrupts you repeatedly about tools.One question per session, max four items; the answer is saved and never asked again.
Never install on its ownTools get added silently; nobody knows what is running.You decide what is installed; the setup stays reviewable.
Skill budgetDozens of skills installed; their descriptions load into every session.Fewer, non-overlapping skills: fewer tokens per session and fewer wrong picks.
Product type decides the setA landing page gets backend tooling; an API gets design presets.Each product type gets the skills that matter for it.
Your rules beat skill defaultsA skill's advice overrides the project's design system or conventions.Project instruction file and design tokens always win.
Net effect for the team: the same task gets the same tools no matter who runs it. Missing tools never block work. Your skill list stays small and deliberate, and every addition is your decision.

Teams

Several devs or agents on one repo

The playbook keeps its state in shared files (profile, ledger, specs, architecture docs). Two agents writing them at once would overwrite each other, so working in parallel follows four rules.

RuleHow it works
Claim before startingEach task block in the plan file has an Owner: line (<dev or agent> · <branch> · since <date>). Pick only a task whose owner is empty, fill it in and commit that line before writing code. Clear it at handoff. A claim with no commits for 2+ days is stale: ask before taking it over.
One branch per task, one working copy per agentTwo agents on the same machine each get their own git worktree. Never two agents on the same files at once; if two tasks need the same files, finish one first.
Shared files merge by ruleLedger: one line per item, newest on top, so on a conflict keep both sides' lines and never delete one. Profile and essentials doc: change only your lines, in a commit with the reason; on a conflict keep the newer verified date and re-run recon if unsure. Specs: one file per feature, never shared.
Before mergingUpdate from the default branch, re-run the narrow tests, and re-check the ledger lines whose files someone else's merged change touched.

After launch: monitoring and spend

Launch is where most guides stop. The playbook keeps going with a short routine, sized to the level like everything else.

WhenWhat happens
Before launchRelease check at the brief's level; every failure fixed or accepted by you · rollback tested once · analytics and consent decided · support contact visible · backups confirmed · paid-API budget recorded and spend visible. Monitoring follows the level: error tracking and uptime alerts are required for a public or paid launch, and recommended for a free beta, where at minimum someone reads the host's error logs daily in week one.
Launch dayDeploy in working hours with someone watching · no unrelated merges · watch errors and the core flow · if the core flow or payments break, the incident flow (next page): contain first, debug second.
First week, daily (10 min)Top 5 new errors · the core-flow funnel against the brief's success metric · yesterday's paid-API spend against the daily share of the budget · user feedback · every issue becomes a ticket with a severity. Severity 1 (data loss, security exposure, payments broken, core flow broken) is fixed the same day.
End of week oneMetric vs target · retro · brief updated with what was learned · plan re-ordered.
WeeklyDependency updates and audit · spend review if the product calls paid APIs (AI, email, rendering, storage): total this week, cost per active user, top 5 users by cost, against your monthly budget. A jump of more than 50% week over week, or a projected overrun, becomes a ticket.
Monthly · every few weeksBackup restore check for a public or paid product · architecture and dead-code survey.

Incidents

When production breaks

One path from "something is wrong" to "it won't happen again". Rule zero: contain first, debug second. The agent never acts on production alone, even for the worst incident; it makes your "yes" fast instead.

#StepWhat the agent doesYour role
1Assess (≤ 5 min)Read-only: what users see, since when, which deploy, how many users. Severity: S1 data loss, security exposure, payments or core flow broken · S2 degraded but usable · S3 cosmetic. Looks up the runbook.—
2ContainProposes the smallest step that stops the harm, in order: turn the feature off (kill switch) → roll back to the last good deploy → disable the broken route. Leaked key: revoke and rotate at the provider first. One message: what's broken, the step, what it undoes, the exact command, ready to run.approve always
3VerifyHealth endpoint answers, error rate back to normal, core flow works end to end; shows the output.—
4Fix forwardOn a branch: failing test that reproduces it → fix → keep the test. Normal review and CI; a hotfix skips CI only if you say so.approve deploy
5Tell usersIf data or security was involved, drafts the notice. Legal notification duties are yours or a lawyer's. Sends nothing itself.approve
6Postmortem≤ 10 lines, blameless, in docs/incidents/<date>-<slug>.md: what users saw, timeline, root cause, what stopped it, what prevents a repeat. Updates the runbook; proposes a new check if one would have caught it.Review
